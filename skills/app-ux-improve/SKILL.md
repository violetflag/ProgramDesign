# 앱 UI/UX 개선

한 번의 요청이 "검토만", "그림만", "코드만"일 수 있다. 그래도 전체 그림은 아래 다섯 단계이며,
사용자가 어디서부터 원하는지 보고 그 단계부터 들어간다. 각 단계의 산출물은 다음 단계의 입력이다.

| 단계 | 하는 일 | 산출물 |
|------|---------|--------|
| 1 둘러보기 | 앱을 실제로 띄우고 주요 화면을 캡처·측정 | 캡처 PNG, axe 결과, 키보드 측정, 대비 표 |
| 2 검토 보고서 | 디자인 비평 + 접근성 리뷰, 번호 붙은 발견 사항 | `design-critique.md`, `accessibility-review.md` |
| 3 개선안 캔버스 | 우선순위 상위 항목을 현재 vs 개선으로 나란히 그림 | Claude Design 캔버스 링크 |
| 4 코드 반영 | 브랜치에서 토큰 → 컴포넌트 → 화면 순으로 고침 | 커밋, CHANGELOG, 버전 |
| 5 검증·보고 | 다시 측정해 전후 수치를 대고 PR + 한국어 보고 | 초안 PR, 보고 메시지 |

자세한 방법은 `references/`에 있다. 필요한 단계의 파일만 읽는다.

- `references/harness.md` — 앱을 헤드리스로 띄우는 법(Tauri의 `invoke` 흉내 내기, 엔진·Vite 띄우기), Playwright 캡처, axe 실행, 테스트 데이터 심기
- `references/review-templates.md` — 두 보고서의 정확한 틀, 심각도 기준, WCAG 항목 번호, 발견 사항을 적는 법
- `references/canvas-guide.md` — 개선안 캔버스를 만드는 법(아트보드 배치 좌표, 메모 쓰기, 현재 화면을 HTML로 옮기는 요령)
- `references/implementation-checklist.md` — 코드로 옮길 때 자주 걸리는 것들(Tailwind 레이어와 포커스 링, 탭·툴바·분할선 ARIA, 포커스 복귀, 알림 시간, 대상 크기, 어두운 테마 토큰, i18n, 버전)
- `references/reporting.md` — CHANGELOG·PR 본문·최종 보고의 양식

스크립트는 `scripts/`에 있고 그대로 실행한다. 매번 새로 짜지 않는다.

- `scripts/axe_capture.js` — 화면 목록(JSON)을 따라 캡처하고 axe-core를 돌려 `results.json`을 남긴다
- `scripts/keyboard_pass.js` — 실제 Tab 입력으로 포커스 순서, `:focus-visible` 표시 여부, 24px 미만 대상을 잰다
- `scripts/contrast.js` — 색 쌍의 WCAG 대비를 계산한다(토큰 교체 전후 비교용)
- `scripts/compare_axe.py` — 두 `results.json`을 비교해 전후 표를 만든다

## 일하는 방식: 이 다섯 가지가 결과를 가른다

**1. 코드만 읽고 평하지 말고 실제로 띄워서 잰다.** 포커스 링이 잘리는지, 대비가 몇 대 1인지, Tab을
몇 번 눌러야 하는지는 코드에서 추측하면 틀린다. 엔진·서버가 있으면 그것도 띄운다(모델 같은 무거운
부분은 없이 돌아가는 모드로). 데스크톱 셸(Tauri 등)은 브라우저에서 `window.__TAURI_INTERNALS__`
같은 호출을 흉내 내면 Vite 개발 서버만으로 거의 모든 화면이 뜬다. 방법은 `references/harness.md`.

**2. 발견마다 번호, 코드 위치, 수치를 단다.** "대비가 낮다"가 아니라 "P1 어두운 테마 주 버튼
`#3f8a63` 위 흰 글씨 4.18:1, `index.css:92`, 권장 `#37805a`(4.8:1)". 번호(U1, P1, O2 …)는 뒤의
캔버스·커밋·PR·보고에서 계속 가리키는 이름이 된다.

**3. 위생과 취향을 나눈다.** 접근성 위반, 깨진 문구, 색 규칙 불일치, 포커스 문제는 "틀린 것"이라 묻지
않고 고친다. 서체·바탕색·배치처럼 취향이 갈리는 것은 먼저 캔버스에 그려 보여 주고, 코드에 넣더라도
초안 PR로 두고 "되돌리기 쉽다"고 말한다. 실제로 사용자는 명조 제목과 한 줄 요약 강조를 보자마자
되돌렸다. 그린 뒤 고르게 하는 편이 빠르다.

**4. 같은 개념은 하나의 UI로.** "메모"가 시점별 메모, 회의 정보의 메모 칸, 녹음 중 메모 칸으로 세 군데
있으면 사용자는 "왜 같은 걸 나눠 놨냐"고 묻는다. 검토할 때 같은 데이터·같은 뜻이 몇 군데에 보이는지
세어 보고, 하나로 합칠 것을 제안한다. 합칠 때는 가장 자주 쓰는 자리를 남긴다.

**5. 사용자가 되돌린 결정은 기록하고 다시 꺼내지 않는다.** CHANGELOG에 "검토 뒤 되돌림"으로 적고,
보고에서도 한 줄 언급한다. 다음 제안에서 같은 것을 또 밀지 않는다.

## 1단계 둘러보기

1. 저장소를 받고 스택을 파악한다. `package.json`, `src-tauri/`, 엔진 폴더, i18n 도구, 릴리스 스크립트
   (`tools/release.py` 같은 것)가 있는지 본다. 이 네 가지는 뒤에서 다 쓴다.
2. `references/harness.md`를 따라 앱을 띄운다. 첫 실행 설정 화면이 길을 막으면 API로 넘긴다
   (`POST /setup/dismiss` 같은 것이 있는지 먼저 찾는다).
3. 테스트 데이터를 심는다. 노트·항목이 6개 이상, 날짜가 오늘·어제·지난주·지난달에 걸치고, 긴 제목과
   짧은 제목, 상태가 다른 것(처리 중, 실패, 즐겨찾기)이 섞여야 목록·배지·날짜 표기가 다 보인다.
   사람 이름은 2~3명 넣어 색 규칙을 볼 수 있게 한다.
4. `scripts/axe_capture.js`에 화면 목록을 주고 돌린다. 기본 화면 + 어두운 테마 + 좁은 창(640·900px)
   + 모달·토스트·메뉴가 열린 상태를 포함한다. 한 화면당 캡처 하나와 axe 결과 하나가 남는다.
5. `scripts/keyboard_pass.js`로 홈·목록·상세 화면의 Tab 순서와 포커스 표시를 잰다.
6. `scripts/contrast.js`로 토큰 색 쌍(글자/바탕, 테두리/바탕, 비활성 버튼 글자)을 계산한다.
7. 캡처를 직접 하나하나 본다. 스크립트는 "위반"만 잡고, "머리가 무겁다", "토글이 설정 패널 같다",
   "같은 사람이 화면마다 다른 색이다" 같은 것은 눈으로만 보인다.

## 2단계 검토 보고서

`references/review-templates.md`의 틀 그대로 두 문서를 쓴다. 디자인 비평은 첫인상 → 사용성(U1…) →
시각적 위계 → 일관성 표 → 접근성 요약 → 잘 된 점 → 우선 고칠 것 → 캡처 목록. 접근성 리뷰는 요약(건수,
치명/주요/경미) → 인지 가능 P → 조작 가능 O → 이해 가능 U → 견고성 R → 대비 표 → 키보드 표 →
낭독기 표 → 고칠 순서.

- "우선 고칠 것"은 체감 크기 × 수정 비용으로 순서를 매기고, 예상 버전(수 버전인지 부 버전인지)을 적는다.
- 잘 된 점을 꼭 넣는다. 이전 검토 지적이 고쳐졌으면 그것도 센다. 다음 검토의 기준선이 된다.
- 보고서는 사용자의 검토 저장소(있으면)에 `reviews/<앱>-<버전>/` 폴더로 두고 캡처 20장 안팎을 `img/`에
  같이 넣는다. 전부 넣지 말고 보고서가 가리키는 것만.

## 3단계 개선안 캔버스

사용자가 "그려 줘"라고 하거나, 3단계 항목이 취향·배치를 바꾸는 것이면 캔버스를 만든다. 방법은
`references/canvas-guide.md`. 핵심 규칙:

- 한 줄에 "현재 · 문제 한 문장" 보드와 "개선 · 바뀐 점 한 문장" 보드를 나란히, 오른쪽 끝에 근거 메모.
- 현재 화면은 캡처를 그대로 붙이지 말고 HTML로 다시 그린다. 그래야 개선 보드와 같은 척도·같은 데이터로
  비교되고, 사용자가 캔버스에서 글자를 고칠 수 있다.
- 숨긴 것(옵션 창, 메뉴)은 작은 보드로 옆에 하나 더 둔다.
- 캔버스 링크를 보고에 넣고, "비공개라 공유 메뉴에서 열어야 다른 사람이 본다"고 알린다.

## 4단계 코드 반영

새 브랜치(`fix/ui-review-<버전>` 또는 `feat/design-<버전>`)에서 작업한다. 순서는 토큰 → 공용 컴포넌트
→ 화면이다. 토큰 한 줄이 화면 수십 개를 바꾸므로 먼저 하고, 그 위에서 화면을 고쳐야 두 번 손대지 않는다.
`references/implementation-checklist.md`를 옆에 두고 간다. 특히:

- 전역 `:focus-visible`은 `@layer base` 안에 둔다. 밖에 두면 유틸리티가 지지 못해 포커스 링이 잘린다.
- 탭은 roving tabindex + ←/→, `aria-controls`/`aria-labelledby`. 툴바는 `role="toolbar"`에 →로 진입,
  Esc로 복귀. 분할선은 `aria-valuenow`.
- 팔레트·모달이 닫히면 열기 전 요소로 포커스를 돌린다. `document.activeElement`는 effect가 아니라
  첫 렌더에서 잡는다(effect에서는 입력칸이 이미 포커스를 가져갔고 StrictMode는 effect를 두 번 돈다).
- 비활성은 투명도 대신 회색 바탕 + 4.5:1 글자색.
- 새 한국어 문구는 i18n 사전에 영어를 넣고 빌드 스크립트를 돌려 누락 0을 확인한다.
- 의존성을 넣었다 뺐으면 lockfile은 추가분만 남도록 정리한다(npm 버전 차이로 `libc` 같은 필드가 통째로
  바뀌면 main의 lockfile을 기준으로 되살린다).
- 버전은 릴리스 스크립트로 올리고 CHANGELOG에 그 버전 절을 쓴다. 화면 구조가 바뀌면 부 버전, 토큰·문구만
  바뀌면 수 버전.

작업 중 사용자가 방향을 바꾸면(서체 되돌리기, 메모장 합치기, 라이브 프리뷰로) 그때그때 커밋을 나눠
반영하고 PR 본문도 최신으로 고친다. PR 본문이 옛 상태를 설명하고 있으면 리뷰어가 헷갈린다.

## 5단계 검증·PR·보고

1. `tsc --noEmit`(또는 그 스택의 타입·린트)을 통과시킨다.
2. 1단계와 같은 스크립트를 같은 화면 목록으로 다시 돌린다. `scripts/compare_axe.py`로 전후 표를 뽑는다.
   목표는 위반 0이지만, 0이 아니면 남은 항목과 이유를 적는다.
3. 키보드 측정을 다시 돌려 Tab 정지 수, 포커스 표시, 포커스 복귀를 수치로 댄다.
4. 캡처를 다시 보고 전후를 눈으로 확인한다. 보고에 넣을 전후 캡처를 고른다.
5. 커밋 메시지는 바뀐 것을 항목으로 적고(번호 U1·P1 등으로 보고서를 가리킨다), 푸시한 뒤 **초안 PR**을
   연다. 본문 양식은 `references/reporting.md`. 모델 이름은 커밋·PR에 적지 않는다.
6. 검토 저장소가 있으면 보고서 끝에 "수정 결과 (버전)" 절을 덧붙이고 전후 수치 표와 수정 후 캡처를
   `img/after/`에 둔다.
7. 사용자에게 한국어로 보고한다. 양식은 `references/reporting.md`. 고친 것, 수치(표), 링크(PR·캔버스),
   의도적으로 남긴 것, 되돌린 것, 다음에 할 수 있는 것 순서.

## 사용자가 바로 수정 지시를 할 때

검토 없이 "이 부분 이렇게 바꿔 줘" 식의 지시가 오면 1~3단계를 건너뛰고 4~5단계만 한다. 그래도
바꾼 화면은 캡처해 보여 주고 axe를 한 번 돌린다. 지시가 여러 개면 번호를 매겨 하나씩 답한다. 질문이
섞여 있으면("이 문구 계속 바뀌는 거야?") 코드를 보고 사실대로 답한다.

지시가 모호하면 가장 그럴듯한 해석으로 끝까지 만든 뒤 "이렇게 이해했다"고 적는다. 묻느라 멈추지
않는다. 단, 데이터를 지우거나 다른 사람 브랜치를 건드리는 일은 확인한다.
